## 1. Project Overview

The Customer Intelligence System is a data analytics and machine learning project designed to help retail businesses understand purchasing behavior, group customers by value and activity, and identify customers who may stop purchasing. It brings together data preparation, exploratory sales analysis, RFM-based customer analysis, clustering, churn modeling, and an interactive dashboard.

### 1.1 Problem Statement
Retail transaction data can be difficult to interpret when stored as individual invoice lines. Business teams need a practical way to summarize sales performance, understand customer groups, and use historical purchasing patterns to estimate customer churn risk.

### 1.2 Project Objectives
- Prepare transaction data for analysis by handling missing values, duplicates, cancellations, and returns appropriately.
- Summarize sales trends, orders, products, countries, and customer activity.
- Calculate customer-level Recency, Frequency, and Monetary (RFM) features.
- Apply K-Means clustering to explore groups of customers with similar purchasing behavior.
- Define a churn target based on a documented observation window and predict churn using historical features only.
- Compare candidate classification models using appropriate evaluation metrics.
- Present results and model outputs through an interactive Streamlit dashboard.

### 1.3 Scope
**Included:** data cleaning and preparation, exploratory data analysis (EDA), RFM features, customer segmentation, churn-label construction, classification and model comparison, visual reporting, and a Streamlit interface.

**Out of scope:** automatic connection to a live point-of-sale system, guaranteed churn prevention, and business decisions made without human review.

## 2. Project Planning

### 2.1 Proposed Workflow
1. **Understand the data:** review the source, columns, data types, date coverage, and data-quality issues.
2. **Clean and validate:** inspect missing customer identifiers and descriptions, duplicates, cancelled invoices, quantities, prices, and date fields. Document the treatment of returns and invalid records.
3. **Perform EDA:** calculate sales and order KPIs and visualize changes over time, products, countries, and customer activity.
4. **Create customer features:** aggregate transaction lines to customer-level RFM measures.
5. **Segment customers:** scale suitable features and fit K-Means; inspect cluster profiles before assigning business interpretations.
6. **Create the churn target:** define the historical feature period and future observation window, then label customers according to repeat-purchase behavior.
7. **Train and evaluate models:** split data appropriately, prevent future information from leaking into features, compare models, and report relevant metrics.
8. **Build the dashboard:** organize analysis and predictions into pages that support clear navigation.
9. **Validate and deliver:** check the pipeline, dashboard, generated artifacts, documentation, and reproducibility instructions.

### 2.2 Deliverables

- Cleaned/aggregated analytical outputs generated locally from the source dataset.
- Customer RFM and segmentation outputs.
- Churn model and evaluation outputs, when generated by the pipeline.
- Interactive Streamlit dashboard.
- Project documentation and presentation materials.

### 2.3 Success Criteria
- The pipeline runs from the documented input and produces the expected artifacts.
- KPI definitions and aggregation levels are clearly documented.
- Customer-level features and labels are created without using information from the future prediction window.
- Model evaluation reports suitable metrics and does not rely on accuracy alone.
- The dashboard distinguishes actual computed results from any demonstration preview.

## 4. Data Source and Data Dictionary

The project is based on the **Online Retail II** dataset from the UCI Machine Learning Repository. The dataset contains retail transaction records. Confirm the exact file/version and date range used in the final run when preparing the submission.

| Field | Meaning | Typical Use |
|---|---|---|
| InvoiceNo | Invoice/transaction identifier | Counting orders; identifying cancellations according to source conventions |
| StockCode | Product/item code | Product-level aggregation |
| Description | Product description | Product reporting; may contain missing values |
| Quantity | Quantity on the invoice line | Sales and return analysis |
| InvoiceDate | Transaction date and time | Monthly trends and time-window definitions |
| UnitPrice | Price per unit | Monetary calculations and validation |
| CustomerID | Customer identifier | Customer-level aggregation, RFM, segmentation, and churn |
| Country | Country as recorded in the dataset | Geographic summaries |

### 4.1 Data Quality Considerations
- Missing CustomerID values limit customer-level analysis and should be handled according to a documented rule.
- Missing product descriptions may affect product-level labels but do not necessarily invalidate every transaction.
- Duplicate rows should be inspected and removed only according to a justified duplicate policy.
- Cancelled invoices and negative quantities can represent cancellations or returns; treatment should be explicit and consistent across KPIs.
- Non-positive prices and invalid dates should be checked before calculating revenue.
- Revenue is commonly calculated as Quantity × UnitPrice, but returns and cancellations require consistent treatment in reported metrics.

## 5. Database Design / Logical Data Model

The source is a flat transaction dataset rather than a relational database. For analysis, it can be represented as a logical model with transaction-line facts and descriptive dimensions.

### 5.1 Logical Entities

**Transaction Line (fact table)**
- InvoiceNo
- StockCode
- CustomerID
- InvoiceDate
- Quantity
- UnitPrice
- Country
- Description (or linked product description)

**Customer (derived dimension)**
- CustomerID (identifier)
- Country (if treated as the customer's recorded country)
- Recency
- Frequency
- Monetary
- Segment label (derived by clustering)
- Churn label / churn score (derived outputs, where available)

**Product (optional logical dimension)**
- StockCode (identifier)
- Description

**Date (optional analytical dimension)**
- Date / month
- Year, month, and other calendar attributes derived from InvoiceDate

### 5.2 Relationships
- One customer can be associated with many transaction lines; CustomerID links customer-level analysis to transaction records.
- One invoice can contain many transaction lines; InvoiceNo groups lines into an order.
- One product code can appear on many transaction lines; StockCode supports product aggregation.
- A date dimension can group transactions by day, month, or year.

These are logical relationships for analytical design. The project does not claim to implement a normalized SQL database unless a separate database implementation is added.

### 5.3 Key Analytical Tables / Outputs
- **Sales aggregates:** sales KPIs, monthly trends, product summaries, and country summaries.
- **RFM customer table:** one row per eligible customer with Recency, Frequency, and Monetary features.
- **Segmentation output:** customer features plus the cluster/segment assignment.
- **Churn dataset and predictions:** customer-level historical features, target labels, predicted classes/scores, and evaluation results, depending on the pipeline outputs generated.

## 6. Analytical and Machine Learning Methodology

### 6.1 Exploratory Data Analysis (EDA)
The dashboard and pipeline are intended to summarize:
- Revenue and order activity over time.
- Order counts based on distinct invoices rather than raw invoice-line counts.
- Product and country performance.
- Customer activity and purchasing patterns.

Each metric should have a clear definition. For example, average order value should be calculated as the chosen net or gross sales measure divided by the corresponding number of distinct valid orders; cancellation and return treatment must match the selected definition.

### 6.2 RFM Analysis
RFM describes customer purchasing behavior:
- **Recency:** time since the customer's most recent purchase relative to a defined reference date.
- **Frequency:** number of purchases/orders in a defined period.
- **Monetary:** total customer spend over a defined period.

The reference date, frequency definition, and revenue/return policy should be stated in the final analysis so scores can be interpreted consistently.

### 6.3 K-Means Customer Segmentation
K-Means groups customers based on selected numerical features. Scaling is normally important because RFM variables can have very different ranges. The number of clusters should be justified through validation and business interpretability. Cluster names should be assigned only after examining actual cluster profiles; they should not be assumed in advance.

### 6.4 Churn Definition and Prediction
Churn is not directly observed in every retail dataset and therefore requires an explicit operational definition. A defensible workflow uses a historical feature window and a separate future observation window. Features must be computed only from the historical window, while the target is determined from behavior in the future window.

For example, a project may label a customer as churned when no qualifying repeat purchase occurs during the defined future window. The final documentation must specify the actual windows and rule used by the implemented pipeline.

### 6.5 Model Evaluation
The project includes a model-comparison workflow. Depending on generated evaluation outputs, suitable measures can include:
- Precision and recall.
- F1-score.
- ROC-AUC and/or PR-AUC where appropriate.
- Confusion matrix.
- Class distribution and baseline comparison.

Because churn classes can be imbalanced, the preferred model should not be selected from accuracy alone. The final report should include only metrics computed by the actual run.

## 10. Privacy, Limitations, and Responsible Use

- Do not commit the original dataset or raw customer-level data to a public repository.
- Check generated files for customer identifiers and other information before publishing them.
- Predictions estimate patterns from historical data; they are not guarantees of future behavior.
- Segments are analytical groupings, not fixed labels of a person's value or intent.
- Data cleaning, returns handling, churn windows, and reference dates can materially affect results.
- If the dashboard is in preview mode, its sample values are illustrative and must not be reported as actual findings.
- Business users should validate model outputs and combine them with domain knowledge before making customer-facing decisions.
